# 2026-09-30 - Data Ingestion Report Pre-Flight Validation built under Reports

- **Sept 30 2026: the first report is built, at `/pages/reports`, from the wireframe (Figma `YMproGZfrFB5jUqPHPxMhk` node `1495:6545`), one report at a time, per direct request from the designer.** The wireframe is a starting point for content and flow only (2.5); it is re-fitted into the shell and the list pattern.
  - **Designer's answers this round:** (1) a person sees the runs on projects they can access, BioData Admin all of them (the Sept 28 decision, 2026-09-28-38, stands); (2) all 21 columns in the table, scrolling sideways; (3) the three status columns are derived from one workflow status, and "Rejected" is a real state; (4) uploading creates a row, with the validation simulated per upload; (5) the report is named "Data Ingestion Report Pre-Flight Validation"; (6) "Additional Filter" stays in, its behaviour to be decided later.
  - **What was built:**
    - **Reports is a keyed section:** `registeredUserNav` gained `reports` (route `/pages/reports`), replacing the inert "Application and System Reports" item. The rail reads "Reports (Own Submissions)" for most roles and "Reports (All Users)" for BioData Admin (`REPORTS_ADMIN_SECTION_LABEL`, the admin IA's own wording). New feature `reports` (every signed-in role; a public user has no Reports section and gets the shell with the restriction), a `wholePageGates` entry, an icon for the admin label, an entry in the `/pages` index, and Home's admin "Reports" quick action is now a real link instead of "Coming soon".
    - **`ReportsShell`** (the Template Finder's shape): three columns, column 2 the section label only, since there is one report (a one-option switcher would be dishonest, 3.10). When a second report exists, column 2 gets the list of reports.
    - **`IngestionReport`:** section header with the count, the sentence for the role, `ToolbarSearch`, the Filter button (Validation status, Submission status, Dataset processing status, Template type, Template, Project, Project status, Ingested by, Ingested month), a disabled "Additional filter", then the table with all 21 columns (about 4,400px wide in a 1,310px card, so it scrolls sideways inside the card and the page never scrolls), the Record ID column pinned while scrolling, sortable columns, and the numbered pagination (50 a page). It fits the viewport with a sticky header (4.2). Search matches record, project, file, template and person; `?q=` pre-fills it.
    - **`ingestion-report-data.ts`** derives every row from a dataset's simulated ingestion (`ingestion.ts`, `datasetStatusFor`), never from a stored status, because the stored status only advances while the project page is open. The three status columns are three readings of that one status: Validation (Processing, Successful, Failed), Submission (Pending, Submitted, Submission failed; confirming the upload counts as submitting once validation passes) and Dataset processing (Queued, Processing, Pending review/approval, Auto-approved, Approved, Rejected). A run that is still moving re-reads the clock once a second and stops when none is.
    - **The simulation, end to end:** uploading a file makes a row (the toast now has a **View report** button that opens the report on that run). It moves on its own from Processing / Pending / Queued to Successful / Submitted / Processing and then Pending review/approval in about 30 seconds; the Prototype tools' "Upload result" tool (and the project chip's Try again) changes how it ends. Verified for all five outcomes: success and partial pass validation (partial has 15% of rows that could not be placed, counted as business rule failures, with both files), the two file failures fail validation (Submission failed, Rejected), and a failure on our side ends Successful, Submitted, Processing with its reason as the submission comment.
    - **Downloads are real files made in the browser** (the uploaded files are never read): the error file lists where, what went wrong and what to do (from `reasonsFor`); the successful file lists the rows added.
    - **"View in Reports"** on the project chip (it was disabled with "Coming soon") now opens the report on that dataset.
    - **A "Rejected" dataset status** was added to the vocabulary (`dataset-data.ts`), for a reviewer turning a dataset down. Validation failure also reads Rejected in the processing column, as in the wireframe.
  - **Sample history:** 60 runs, deterministic and anchored to a fixed day (a clock would make server and browser disagree and break hydration), from the placeholder cast on the app's four projects and its own template list. A person uploads to their own project and a few colleagues to it; Olivia Wyatt only to hers, so a registered user sees a believable 25 of the 60 and BioData Admin all. Reviewer and approver columns are filled for the sample (Jane, the admin persona, and "System" for auto-approved). Real uploads have no reviewer yet: nobody reviews them, because review is not built.
  - **Departures from the wireframe, on purpose:**
    - Filter and search follow the list pattern (a Filter button applying as you choose) instead of 12 always-open fields, chips and Apply Filter; the four project filters became one Project section plus Project status; **"Project timeline" is left out** until the date-range filter is designed, and "Ingested Timeline" is a month filter.
    - Numbered pagination replaces "50 of 1797" and a progress bar.
    - Column names are sentence case and spelled out ("Business rule failures", "Download successful file"; the wireframe had "(PF)" and "Sucessful"). An empty cell is empty and "None" says a download does not apply (no "NA" or dashes, 2.3).
    - The people are the placeholder cast and the projects the app's own: the wireframe's invented people and Victorian place names are not used (0.3).
    - The **Record ID is the dataset's own ID** (`DS-2026-…`), not a second `REC-…` number.
    - Chips are not shown; Filter shows the count.
  - **Typography (2.9, 0.6 item 8):** measured live. Everything is Barlow. Cells are 14px regular; the Record ID 14px medium; numbers tabular; header, badge and button text are the design system components' own (12px semibold headers and badges, 14px semibold links); the heading is the SectionHeader's 18px semibold; the count of failures is 14px medium in the error text colour (4.8:1). No new type layer; the roles copy the Template Finder and project list cells. The header colour and the page-number contrast are the design system's own (left as is, 2026-09-30-16).
  - **Verified:** `tsc`, `eslint --max-warnings=0` on every touched file, `npm run check:contracts` and a production `next build` pass. Live with Playwright, zero console errors: 21 columns and 50 rows; the table scrolls sideways and the page does not; the rail and Home reach it for the right roles with the right label; BioData Admin 60 rows, registered and privileged users 25, a public user the restriction; search, filter (Failed gives the 6 failed runs), sort, page 2 (10 rows) and the error-file download; a real upload through the form, the toast's View report, the row moving through its statuses, and the failure, partial and our-side outcomes with their files.
  - **Not done, for the designer:**
    1. **Review and approval:** the reviewer and approver columns are filled only in the sample history. Nothing lets an admin review or approve a real upload yet (that is the next piece: it also decides what "Under review" means and who is notified).
    2. **"Additional filter"** is a visible, disabled control until its behaviour is decided.
    3. **Template and Template type:** the app's template list has eight templates and all are Flora, so the Template type filter has one option. A file's template is guessed from its name in the simulation; real validation would read it from the file.
    4. **Column 2** is the section label only. The Sept 28 note proposed an Export CSV action there; it was not added because the wireframe does not draw it.
    5. The keyboard pass on the table (sorting, Filter, downloads with Tab, Arrows, Enter, Escape) was exercised by mouse and script, not by a full keyboard-only walk.
