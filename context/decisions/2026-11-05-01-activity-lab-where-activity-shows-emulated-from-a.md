# 2026-11-05 - Activity lab: where Activity shows, emulated from a dataset submitted for approval

- **Nov 5 2026: a lab at `/proto/activity-notifications`.** The designer asked whether activity notifications were built (they were not: the Workflows page only marks its Activity lines Proposed, `2026-11-03-01`) and described the job: a user submits a dataset for approval and the admin is told; once the admin approves it, the user sees "dataset on project has been approved" and can "view project". Then: "there's no activity engine per se, but just to emulate", and yes to a small opt-in slot on the header for a bell.
  Job and principles first (0.10): who is told what, on which screen. 1 Say less (a row says one thing and offers one next step; an empty list says what will appear), 5 Make it obvious (what happened, on which project, where to go; unread is visible), 6 Reveal in steps (a count first, the list one press away), 7 Design every state (nothing, one, many, read and unread, the admin, the uploader, the signed-out visitor), 3 One system. Where they pull apart: Say less against Make it obvious (a panel is always read, a bell only when pressed). Closest pages: the `home-cleanup` lab for hosting the real Home in the real shell, Home's own task rows and "Your requests" heading, the audit feed's day labels, the Template Finder's section header, the rail's red count.
  **Built (lab only, 5.4).** Three options behind the layout tool, `?option=`: **A** a section on Home above the rest of it (always in view, takes about 270px from Home); **B** its own screen, All activity and Unread in column 2 (the longest list, one more place to go to); **C** a bell after the Add menu with the list in a popover (no room taken, found only by its count). The same row in all three: a FeaturedIcon (an upload for a dataset waiting, a check for one approved), a 14/500 title and a 14/400 line under it, the date at the right (`whenLabel`), a dot for unread, and one link-style button with the forward arrow ("Review dataset", "View project"). Mark all as read. A signed-out visitor gets the restricted state with all three columns, as Activity is about a person's own work.
  **The emulation.** No engine. `activity-store.ts` holds the datasets the example has submitted and what has been opened (kept in this browser only, apart from the product's dataset store so the example adds nothing to the product's lists); `activityFor` reads what each role would be told from them, the way the product would read its dataset store: an admin is told of a dataset waiting (Under review, no approval), the uploader of its approval (`approveDataset` records who and when). The Prototype tools bar has an "Example" menu: a dataset is submitted, the admin approves the oldest, start again; "Viewing as" switches between the two sides. Projects are the project list's published ones; the uploader is the product's current user (Olivia Wyatt) and the approver is a placeholder admin (Phoenix Baker, 0.3). Every line is Proposed wording.
  **Shared code touched, additively.** `AppHeader` takes an optional `activity` slot after the Add menu; nothing in the product passes it, so no header changes. `whenLabel` is exported from `audit-feed.tsx` (it was private) rather than copied. No new component (1.4): everything is the design system's (`Button`, `ButtonUtility`, `CountBadge`, `FeaturedIcon`, `Popover`, `SectionHeader`, `Tabs`).
  Verified: `tsc`, `eslint` on the lab, `AppHeader`, `audit-feed` and the labs index, and `check:contracts` pass. Live at 1440x900, scrollbars drawn, zero console errors: empty states for the admin and the uploader; two datasets submitted give the admin two rows and a count of 2; opening "Review dataset" goes to the project's Datasets tab with the role kept and marks that row read; Mark all as read clears the rest; the admin approves, the uploader sees "Dataset DS-2026-00901 on Adelaide Hills Bushland Survey has been approved" with "Approved by Phoenix Baker" and "View project" (the project's page, role kept); the admin still has the other one waiting.
