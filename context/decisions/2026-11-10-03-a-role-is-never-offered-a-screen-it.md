# 2026-11-10 - A role is never offered a screen it cannot open (contract 3.15)

- **Nov 10 2026: a new clause, 3.15, and the fixes behind it.** The designer, with a screenshot of a signed-out visitor on the Data ingestion stress test's restriction: "Identify these cases, never take the user to the screen if they do not have role permission to access that particular screen. Creates so much bloat." Job: a person of any role moves through the product and is never sent to a page that only says it is not for them. Principles: 1 Say less (a refusal page is noise), 5 Make it obvious (a control that goes nowhere useful is a false promise), 7 Design every state (each role). Closest page: the Prototype tools' Pages map, which already hid the screens a role cannot open (`availability`).
  **One list, one hook.** `lib/page-access.ts` now holds `wholePageGates` (it was in `app/_prototype-tools/page-gates.ts`, which re-exports it so the tools keep their import), with `isPageBlockedFor` (a query string is now ignored) and `canOpenPath`. `lib/use-can-open.ts` is the hook a control asks. The scope map gives both files to the `shell` rules.
  **Fixed.** (1) The `/pages` index lists only what the chosen "Open screens as" role can open (it defaults to the signed-out role), and its stress-test row said "Everyone" when the feature is registered users and above (since 30 Oct): now "Signed in". (2) A dataset's page: "Upload a corrected file" and "View in Reports" are left out for a role that cannot open them. (3) The upload problem buttons (`IngestionProblems`) likewise. (4) The upload toast's "View report" is only offered where Reports opens. (5) Map visualise: the back link to the report and the Reports crumbs are replaced by the plain Explore trail for a role without Reports. (6) Home's quick actions and tasks (Data licence request, Sensitive species nomination, the task links) check the same list. (7) The docs data model page's "Open the data ingestion stress test" opens as a Registered User, since a doc page has no role. (8) On a restricted record page (nomination, DLA, DSA) the breadcrumb is a plain label, no longer a link to the gated list.
  **Found by crawling, not guessing.** Playwright as Public, Registered, Privileged and BioData User over 18 seed screens collecting every link and opening each target as that role: one link to a screen the role cannot open (the nomination crumb). A second pass opened every gated address as each role and listed its links: none to another gated screen now. The `/pages` index per role: Public 22 rows and none blocked, Registered 46 and none blocked. Zero console errors. `tsc` clean, `eslint` clean on the touched files, `check:contracts` passes.
  **Not changed on purpose.** A signed-out visitor pressing Upload or Export gets the sign-up prompt, not a refusal page (3.4's gated actions). Typing a gated address still shows the restriction with all three columns (3.7). The unused `FlaggedHomeQueue` links to a page that has no role gate.
  **Not verified.** The dataset page and upload problem buttons were checked by reading the code and the types, not by driving a failed upload in a browser as each role. The crawl does not click buttons and menu items; it reads anchors, so a `router.push` is covered only by the grep of every call site to a gated address.
  **Enforcement.** `REVIEW` (a crawl as each role). A first occurrence (0.8), so no `AUTO` check; one is due if it comes back. A cheap one would compare each `screen-index.ts` access label with the matrix.
  **Open, for the designer (0.4).** (1) Should the `/pages` index keep a way to see the screens a role cannot open (a toggle), or is hiding them right, as the Pages map does? (2) The restriction pages are still reachable by address; if a signed-out visitor on one should be offered Log in rather than Home, that is a copy and action change on each. (3) The Prototype tools' role switch goes Home when a role cannot see the page; whether it should do the same for a signed-in role is unchanged. Not committed.
