# 2026-10-26 - Custom concepts: columns added to a sheet at upload are flagged for admin approval

- **Oct 26 2026: A column an uploader adds to a data sheet that BioData does not have is now a "custom concept": it is shown to the uploader in a section of its own, flagged for admin approval, and decided by an admin on the Flagged concepts page.** The designer: "Data ingestion - if a user, during data upload, adds a new column (or concept), then those concepts need to be flagged for admin approval. If a concept doesn't exist in the control vocabs and the user is submitting a concept they've added on the excel sheet during data upload, let's create a section to show 'custom' concepts."
  - **Job (0.10):** a registered or privileged user uploads a workbook to a project and needs to know which of their columns BioData does not know, and that an admin will decide on them; a BioData admin needs one queue of those concepts and one decision for each.
  - **Principles at stake:** 4 Tell the truth (a concept is found from the real file's column headings, never invented or guessed), 1 Say less (the section exists only when there is a custom concept; no empty "none" state), 5 Make it obvious (every concept says where it is and where it stands), 6 Reveal in steps (the form's own section, then the ingestion detail, then the admin's queue), 7 Design every state (waiting, approved, not approved, none, a failed ingestion, each role), 3 One system. Where they pull: Say less against Make it obvious for a person who uploads a clean file (no section, no word about concepts); and Tell the truth against keeping a file's contents (below).
  - **The word, from the repo.** The stress-test lab already treats a column the schema does not know as "a real custom property" and "flags it for review rather than silently accepting it" (`app/proto/data-model-stress-test/page.tsx`), and a record has a "Custom properties" section (`survey-data.ts`). "Concept" is the product's word for a record's data item (`ConceptRows`, "Flagged concepts", `Concept that differs` with the columns icon). A custom concept is the name of such a column; it is one more kind of the thing the admin already flags.
  - **What is known, so what is custom (`dataset-upload/custom-concepts.ts`).** A heading is known if it is a field or alias of the data model (`config/data-model-schema.ts`), a BDBSA column key the model maps, a structural or identity column the ingestion reads, the name of a controlled vocabulary (read from the store), or a custom concept an admin approved. Headings are compared as the model compares them (case, spaces, underscores, slashes and hyphens ignored), so "soil_ph" and "Soil pH" are one concept. Anything else is custom. Hidden sheets (lookups) are skipped, and a sheet whose first row has fewer than two headings is not a table and is skipped.
  - **What is kept.** When a workbook is added, its first row is read in the browser (`readWorkbookColumns`, SheetJS, the first two rows only) and the dataset keeps each visible sheet's name and the headings with their column letters, never a value: the dataset store's rule is "never their contents", and a sample value can be a restricted species' location. The cost is that an admin deciding on a concept sees its name and where it is, not what it holds.
  - **The three places it shows:**
    1. **The upload form (the uploader, before sending).** A conditional section between "Upload files" and "Data upload acknowledgement", in column 2 and in the step count ("Step 2 of 3"), only while the files hold some. It lists each concept with its sheet and column ("Sheet Species, column D", "and 1 other place"; the file's name leads only when there are several files) and says what happens next. Nothing in it is required: the concepts are flagged and the upload goes ahead. With a clean file the form is exactly as before, two steps.
    2. **The dataset's ingestion detail (the uploader, after).** The chip's popover on the project page and the Validation tab of the dataset's own page both draw `IngestionDetail`, so one section serves both: "Custom concepts" with a count, and a row for each with its status badge (Awaiting approval, Approved, Not approved with the admin's reason). The explanation line shows only while one is waiting.
    3. **The Flagged concepts page (the admin).** The page has two kinds, switched in column 2 the way All and My are (a vertical switch with an icon on each: Questionable values with the flag, Custom concepts with the columns icon, each with its count). The custom view is laid out like the first (column 2 is the queue with a progress bar, Waiting and Decided; main is a `FormPage` for the one in focus). One item is one concept, not one upload: "Soil pH" added by three datasets is one item that lists all three, and one decision covers them. The decision is Approve or Do not approve, with a reason required to decline; Undo is on the toast. Approved, a concept is known to every later upload; not approved, it is flagged again the next time it is uploaded.
  - **What an upload does meanwhile (recommendation, decided here, for the designer to change):** the data goes in as usual and the concept is flagged, the way a questionable value stays on its record while it is reviewed. The other readings (hold the column back until approved; refuse the upload) were not built. A dataset whose ingestion fails adds nothing, so its concepts are not offered for approval and its section is not shown; the corrected upload flags them, and a retry that succeeds brings them back.
  - **Reuse (0.9):** `IngestionDetail`, `FormPage` and `FormRow`, the review screen's queue and toast pattern, `AgreementScopeNav`'s switch, `Badge`, `CountBadge`, `RadioGroup`, `TextArea`, `ProgressBarBase`. No new component, so no override. The one list of rows is shared by the form section and the ingestion detail (`CustomConceptRows`), so the two cannot drift. It is a flat list with a line between the rows, not a box: a box with corners inside the dataset's card would have to be concentric with it (2.13), and the lines say all there is to say.
  - **Type (2.9, from the siblings):** a concept's name is 14/600 primary and its location 12/400 tertiary, the same two layers as the ingestion's reasons (`ReasonList`: title 14/600, where 12/400); the explanation is 12/400 tertiary as the run's "About 25 seconds left"; status is the design system's `Badge`; the admin's title is `SectionHeader.Heading`. Measured: 14px/600 and 12px/400 in Barlow, contrast 14.4:1 and 5.26:1 on the dataset page (5.13:1 in the admin's "where" line), zero radius on the list.
  - **Checked live (Playwright, scrollbars drawn, real files):** a workbook with standard columns only shows no section and two steps; a workbook with three added columns (one repeated on two sheets under two spellings, one on a hidden lookup sheet) shows exactly three concepts, "Soil pH" merged across its two places, the hidden sheet ignored; the form's step count and column 2 follow; the upload saves three pending concepts; the chip's popover and the dataset page show them with "Awaiting approval"; the admin sees three items and the kind tabs read "Questionable values 16" and "Custom concepts 3"; saving with nothing chosen, and declining without a reason, are each refused with "Details missing"; one declined with a reason and one approved give "Not approved" with the reason and "Approved" to the uploader, and Undo's toast is shown; a second upload of the same file flags "Soil pH" (not approved) and "Observer notes" (still waiting) and not "Canopy gap (m)" (approved); forcing the ingestion to fail empties the admin queue and its count and the section, and a success brings the three back; the decision's radios are reachable and chosen by the arrow keys; a Registered User opening the page gets the restriction. Zero console errors throughout. `tsc`, `eslint` on every touched file and `npm run check:contracts` pass (the first run caught a 4.1b violation: tabs in a `FormPage` file; the switch is now in `flagged-kind-nav.tsx`).
  - **Test files:** `context/fixtures/sample_workbook_with_custom_columns.xlsx` (headings the data model knows on the Site and Species sheets, plus "Soil pH", "Canopy gap (m)", "soil_ph" and "Observer notes", and a hidden lookup sheet) and `sample_workbook_standard_columns.xlsx` (the standard ones only), to drag into Upload dataset. They are test data (values like a soil pH of 6.4 are made up), kept out of `public/` so they are not deployed.
  - **Not checked:** touch and the narrow layout (column 2 of the admin page is hidden under `lg`, as the first view's is); Safari and Firefox; a screen reader on the new section and the decision radios; a real `.xls` (the old format), a very large workbook, and one laid out as a form with no heading row (the BAM scoresheet is one: it was not tried, and its first row may be read as headings, which would flag labels as concepts); two workbooks in one upload; a BioData Super Admin and a Privileged Admin on the page.
  - **Not done, on purpose:** the admin's Home. It is parked (`2026-10-25-07`), and its Flagged concepts queue still counts only questionable values, so an admin learns of a waiting custom concept from the Flagged concepts page's tab count, not from Home. The Data Ingestion Report (Reports) has no column or filter for custom concepts. The rail's red "3" is unchanged.
  - **Open, for the designer (0.4):**
    1. **What "approved" does.** Today it makes the concept known to later uploads and tells the uploader. It does not add an entry to a controlled vocabulary, and a vocabulary is a Super Admin's alone (REQ-18.1: a BioData Admin has no access), while the Flagged concepts page is for BioData Admins and Privileged Admins. Does an admin's approval stand for itself, or is it a request that a Super Admin turns into a vocabulary entry? That decides whether the Controlled Vocabulary screens need a way to receive an approved concept.
    2. **What the data does if it is not approved.** The values stay in the uploaded records as a custom property of each record. Should a not-approved concept's values be removed, marked, or left?
    3. **Whether the uploader says what a concept is.** An admin sees a name and a place only. A short "what is it" field per concept in the upload section would help the decision; it was not added because it was not asked for.
    4. **Where an admin first learns of one,** with Home parked: the tab count, a badge on the rail's Home icon, or a row in Home's queue.
    5. **One approval across projects.** A concept approved for one project is known to all of them. Per project would be the other reading.
    6. **The known-names list is copied.** The stress-test lab's identity columns are repeated in `custom-concepts.ts` because a product file cannot import from a lab (5.4); they should be one list in `config/data-model-schema.ts`.
