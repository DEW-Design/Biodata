# 2026-10-26 - Nominations: an admin's nomination follows the same workflow as every role

- **Oct 26 2026: a BioData Admin or Super Admin can no longer approve their own sensitive species nomination as they make it. It is submitted to the panel like a registered user's.** The designer: "an admin cannot directly submit an approved nomination (for sensitive species), it has to follow the same workflow as the registered users." This takes back the version 2 rule of 12 Oct 2026 ("a BioData Admin or Super Admin who nominates can approve it at once"), which the version 3 screens kept.
  - **Principles at stake (0.10):** 3 One system (one workflow for every role: draft, submitted, under review, accepted or rejected), 7 Design every state and each role (a role removes features, it does not get a different screen), 4 Tell the truth (a nomination reads as accepted only after the panel accepted it, and its audit history shows who moved it).
  - **What changed.**
    1. The new nomination form (`nomination-form.tsx`, `new-nomination-page.tsx`) lost the approve path: the props `canApprove` and `onApprove`, the "Approve nomination" button with its check icon, the "Review and approve" step title, and the ratings an admin had to set before approving. An admin's form is now the registered user's: Species (or Location), What to protect, Review and submit, ending in "Submit nomination", with no Data release fields.
    2. `approveNomination` (the store function that saved a nomination as submitted and accepted it in one go) is deleted. A nomination always starts as a draft or as submitted (`saveNomination`) and only the panel's actions move it on (`startNominationReview`, `acceptNomination`, `rejectNomination`, `returnNomination`).
    3. The words that described the old path were corrected (the list page and form header comments, the `/pages` index descriptions of the two nominate screens).
  - **Kept, because the designer did not ask for it to change.** An admin still edits any nomination past its draft (Save changes keeps its status) and sets the data release risk and user access level of what is protected, in the edit form and on the record page while it is under review. The Start review, Accept, Return and Reject actions are still the card's, shown to the roles that can review.
  - **Checked.** `npx tsc --noEmit` clean; `npx eslint` clean on the nominations folders; `npm run check:contracts` passes. Live (Playwright, 1500 x 950, zero console errors), a new species nomination walked through all three steps as BioData Super Admin, BioData Admin and Registered User: the same three sections, no Data release rows on any step, the last step's button "Submit nomination", and the result a record NSS-2026-00023 with status Submitted and the toast "Nomination submitted: NSS-2026-00023 is with the sensitive species panel"; the admin roles then see "Start review" on it and the Registered User sees "Edit nomination" (its own). An admin's edit of a submitted nomination still opens on What to protect with its Data release rows and "Save changes".
  - **Not checked.** A location nomination submitted to the end (the area picker was not driven; the last step's button and the save are the species form's own code); touch.
  - **Open, for the designer (0.4).** An admin who nominates can now start the review of their own nomination and accept it, because Start review and Accept are shown to every reviewer on every submitted nomination. That is the same workflow as a registered user's in the screens, but it is two steps instead of one. Should the person who nominated be unable to review their own nomination (the card shows no Start review or Accept on it)? It is one test on the record page (`nominator.name === CURRENT_USER_NAME`).
