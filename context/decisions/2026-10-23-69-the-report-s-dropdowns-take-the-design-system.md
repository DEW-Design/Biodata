# 2026-10-23 - The report's dropdowns take the design system's label above them; Select inlineLabel removed

- **Oct 23 2026: The label drawn inside a dropdown's trigger is taken out. The Data Validation Error Report's Project and Dataset use the design system's `Select` label, above the field.** The designer, with a crop of the two dropdowns ("Project  BD-5137 · Flinders Ranges Reptile Atlas", "Dataset  DS-2026-01003 · flinders_bushland_a...01.xlsx"): "that component design is an antipattern - doesn't align to design system."
  - **Clauses at stake, named (0.1):** 2.5 (Figma is the source of truth: the design system's `Select` is a label above, a field, a hint; no frame draws a label inside the trigger), 1.2 and 1.5 (no lookalike; a real component is not patched to serve one screen's need), 3 One system and 4 Tell the truth in the principles. My own entry, `2026-10-23-65`, had added the opt-in prop `inlineLabel` to `Select` (1.6 allows an additive prop, but a prop is not a licence for a pattern the design system does not draw) and said the alternative, the label above, "is the Select's existing `label` prop". It was the wrong choice and I had named the right one; the designer's reading of the screenshot is correct.
  - **The fault, in the design system's terms:** a label inside the trigger sits in the same line, size and weight band as the value, so "Project" and "BD-5137" read as one string and the label is lost when the value is long; it is also a field with two kinds of text in one box, which no other field in the product has. A persistent label above the field is the pattern everywhere else (the form pattern, 4.1 item 3; "placeholder is not a label").
  - **The change:**
    1. `Select`'s `inlineLabel` prop is **removed** (the prop, its `<p>`, its `aria-label` fallback, its row in the API table on `/components/select`). `grep inlineLabel` finds nothing outside the history in `context/decisions/`.
    2. The report's two dropdowns have `label="Project"` and `label="Dataset"`: the component's own `Label` (14px, medium, above, 6px from the field, associated to the field, so the name is read once).
    3. The toolbar row aligns its controls **by their foot** while it has a labelled field (`items-end` when `parameters.inline`, `items-center` for every other report, which is as it was): measured at 1686, 1440 and 1280 wide, search, Filter, both dropdowns and Columns have the same bottom edge, one row; the row is 62px high (it was 36px).
    4. The screens index's "Open screens as" picker, which `-65` had given an inline label, now has the same `label` above it (its row was already aligned by its foot: select and search bottoms equal, 187px).
    5. CONTRACTS 4.6 (the exception's sentence), the `parameters.inline` comment and `/patterns/report-toolbar` say "the design system's own label above it"; `.claude/rules` regenerated.
  - **What stays from `-66`:** the truncation strategy (a title cut at a word, a file name cut in the middle keeping its version and extension, the list as wide as its longest row, the full text as the tooltip) was asked for separately and is not what was objected to. It has more room now: the label was costing about 52px of the trigger, so at 1440 the dataset reads "DS-2026-01003 · flinders_bushland_asse...01.xlsx" and at 1686 the project name is whole.
  - **The cost, said plainly:** 26px of toolbar. At 1440x800 the report's table has about 26px less (the table body is 319px; it keeps its 24rem minimum, 4.6). If that is too much, the only way to take it back that the design system allows is the Parameters popover (labelled fields behind one button), which the designer moved away from on 23 Oct ("I feel having parameters is weird"); say so and it comes back as the default.
  - **Checked live (Playwright, Super Admin; zero console errors):** the three widths above, the screens index. `npx tsc --noEmit`, `npx eslint` on the touched files and `npm run check:contracts` clean.
  - **Not checked:** Registered User and BioData Admin on the report (the row has no role-dependent part; both were checked when the dropdowns were first built, `-63`), touch, Safari.
  - **Open, for the designer:** whether the 26px is acceptable; and whether the unlabelled search and Filter beside two labelled fields read well (the alternative, a visually hidden label, would not change what a person sees).
