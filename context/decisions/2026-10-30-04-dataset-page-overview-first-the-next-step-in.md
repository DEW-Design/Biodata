# 2026-10-30 - Dataset page: Overview first, the next step in the card, Approve for an admin

- **Oct 30 2026: a dataset's own page (`?view=datasets&dataset=<id>`) is brought in line with the other record pages.** The designer asked for a UX look at it ("it doesn't quite sit well"); a review (findings 1 to 7, in the session) was answered: "1. Yes. 2. Overview (Project overview). 3. Dataset has its own metadata." Read as: a BioData Admin approves a dataset that is under review; the first tab is an Overview, laid out like the project's; and what that Overview holds is the dataset's own facts, not the project's.
  - **Principles at stake (0.10):** 5 Make it obvious (the next step and who acts are in the card), 3 One system (the record-page pattern, 4.6, and the shared audit feed), 1 Say less (the run's buttons were on the Validation card and nowhere else; they are not said twice), 6 Reveal in steps (what the dataset is first, the checks behind a tab). 3 and 1 pulled apart where a dataset has no next step (an approved one): its card then has no action bar, rather than an empty one.
  - **What changed.**
    1. **Tabs: Overview, Validation, Audit Log** (Details became Overview and moved first; icon `Grid01`, 3.13). Its card is full width like the other record pages (it was capped at 768px beside two full-width tabs). Rows: file, rows, records added (with "Open project records", the project's records tab; the tab is not filtered to the dataset, so the link says so), data licence, security classification, First Nations consideration, IIA reference where there is one. Nothing else is shown: the sheet's other dataset fields (dates, methods, permits, restrictions, privacy declaration) are not in the dataset's data, so they are not drawn (0.3).
    2. **The next step is in the card** (4.6 item 2, `RecordActionBar onDark`). A dataset that did not go in offers "Upload a corrected file", or "Try again" for a fault on our side, as its one button; "View in Reports" is in the "..." menu. A BioData Admin on a dataset that is under review gets "Approve" as the one button and the upload in the menu. An approved dataset with nothing to fix has no actions. `IngestionDetail` and `IngestionProblems` take `actions={false}` (opt-in; every other caller is unchanged) so the Validation card no longer repeats the buttons (one control per action, 3.12).
    3. **The file is in the card** as a fact, since the title is the dataset's ID and the file is what a person recognises.
    4. **Audit Log is the shared feed.** "Show all changes" opens `AuditFeed` (as DLA, DSA and nominations do, 4.6 item 6); it was a hand-built list of `RecordRow`s.
    5. **Approve is real in the preview.** A new feature key `datasetReview` (`config/role-access.config.ts`, BioData Admin and Super Admin through the bypass, no other role) gates it. `approveDataset(id)` in the dataset store records who and when; an approval wins over the status a sample or an upload would otherwise show (`withApproval`), so the dataset's page, the Datasets tab and its audit feed agree, and it survives a reload.
    6. **CONTRACTS 4.6 item 7** now says what a dataset record is (Overview, Validation, Audit Log, next step in its card) and keeps Controlled Vocabulary as the one record still open; the scoped rule files were regenerated.
  - **Not changed, on purpose.** The header: at 1440px the five-level crumb (Home, Projects, the project, Datasets, the ID) wraps and the header grows from 65px to 104px, so the page drops 39px on the way in from the tab (no wrap at 1716px). That is the shared `AppHeader`, a change for the designer to decide. The Datasets tab's own "latest upload" card keeps its buttons (it is the project-level view of that run, not the dataset's page).
  - **Checked.** `npx tsc --noEmit`, `npx eslint` on the touched files and `npm run check:contracts` pass. Live (Playwright, 1716 x 1030, zero console errors), as Registered User and BioData Admin on all three sample datasets: the tabs read Overview, Validation, Audit Log and open on Overview; the failed dataset's card has "Upload a corrected file" and the menu "View in Reports", which opens the upload page; the under-review dataset has "Upload a corrected file" for the Registered User and "Approve" (with the upload and "View in Reports" in the menu) for the Admin; the approved one has no action; the Validation tab has no buttons; the Overview card is the panel's full width (1604 of 1652px); Approve moves the dataset to Approved in its card, the audit log (a new "Approved" line by the placeholder user, "Current"), the Datasets list and after a reload.
  - **Not checked.** Touch and narrow windows; a dataset still running (the card's actions while its run is in progress); the upload step of "Upload a corrected file" beyond reaching the upload page; roles other than Registered User and BioData Admin on this page (Super Admin passes the same gate).
  - **Open, for the designer (0.4).** (1) **Who reviews, and is there a Reject?** Approve is built because you said an admin approves; the statuses already include "Rejected", but no Reject action was asked for, so none exists. (2) **The two reports that read datasets** (`project-detail-report.tsx`, `records-report.tsx`) read the stored datasets and do not know about an approval yet (1.3, flow-through); it matters once approvals are real data. (3) The "Project BD-5039" fact in the card repeats the crumb's project; kept, since "Dataset has its own metadata" was read as about the Overview. (4) The header wrap above. (5) The sheet's dataset fields (dates, methods, permits, restrictions, privacy declaration) are the Overview's next rows if the dataset's data model grows them: that is the project flow's question (the business is considering a dataset step in Add Project).
