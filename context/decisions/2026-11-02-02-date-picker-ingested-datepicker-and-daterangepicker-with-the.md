# 2026-11-02 - Date picker ingested: DatePicker and DateRangePicker, with the pick held in a draft

- **Nov 2 2026: the Untitled UI Date picker is brought through the ingestion workflow.** The designer: "Ingested the datepicker component, please follow the component ingestion rules from context and contracts." The Untitled UI CLI had added `components/application/date-picker/` (`date-picker.tsx`, `date-range-picker.tsx`, `calendar.tsx`, `range-calendar.tsx`, `cell.tsx`) and `hooks/use-breakpoint.ts`. It is documented at `/components/date-picker`.
  - **Ingest hygiene (1.8), before anything else.** `git status` and `git diff` after the CLI: only new files, plus `package.json` and `package-lock.json`. No tracked component was changed or reverted. The CLI did change the dependencies: `react-aria` 3.52.1 to 3.53.1 and `react-aria-components` 1.21.1 to 1.22.1 for the whole app, and `@internationalized/date` (until then only reached through them) is a direct dependency. After the bump, a live pass over the screens that use those libraries shows no console error and nothing changed: the Add Project and project card date fields open their calendars, a Select opens and Escape closes it, the Filter menu opens a submenu, and the Input, Select, Dropdown, Table and custom Date picker doc pages and the DLA, nominations and report screens load.
  - **Authorised (1.4, 9.2).** One override per file, `OVR-013` (`calendar.tsx`), `OVR-014` (`cell.tsx`), `OVR-015` (`date-picker.tsx`), `OVR-016` (`date-range-picker.tsx`), `OVR-017` (`range-calendar.tsx`), designer and approver Sai Maniganahalli, review by 25 Mar 2027 as the other ingests. They stay in `components/application/`, where the CLI put them and where the carousel (`OVR-012`) is. The five files are in `contracts/component-inventory.json` (`--update-baseline`; the ratchet baseline did not move).
  - **What the check found, and what was fixed (0.6 item 3).** 12 violations at first. Five text buttons without an icon (3.12): Cancel is `XClose`, Apply is `Check`, and the calendar's Today is `CalendarCheck01` (the trigger is `Calendar`; two actions never share an icon). Two dead `text-md` on the dash between the range's two date fields (2.1): `text-sm`, the size of the fields. Five files with no override (1.4): above.
  - **What the QA found that the check cannot (0.6 items 4, 8, 11).** (1) **The pick was not held.** Every pick changed the date at once and Cancel closed the calendar and left the pick in place, and so did Escape and a press outside: a Cancel that did not cancel (1.9: Escape closes and cancels, it never changes a committed value). Both pickers now hold the pick, and a preset, in a draft: it becomes the date, and `onChange` fires once, on Apply; Cancel, Escape and a press outside call `onCancel` and keep the date as it was; the calendar reopens on the date it holds. (2) **The trigger's accessible name was "Calendar Date picker",** which did not contain the words on the button ("Select date", "Nov 15, 2026") and never said the date (WCAG 2.5.3): it leads with the date or the range now ("Nov 15, 2026 Date picker"). (3) **Between `md` and `lg` a range had no presets:** the column is `lg` and up and the three short ones above the grid were drawn only below `md`; `showPresetsOnDesktop` is set from `lg` down. (4) The popovers are portaled out of the page, so they carry `font-barlow` (2.2); measured Barlow on the popover, the dialog and a day cell. (5) The month heading is an `h2`, and in a doc page the doc site's `.prose-doc h2` made it 20px with a 48px margin: `!` on every property it sets (2.7); measured 14px/600 with no margin inside the doc page and in the popover. (6) The range's preset rows were 36px and are 40px, measured (2.16, the designer's 30 Oct rule that rows are not exempt). (7) "Today" was read when the file loaded, so a page open past midnight kept yesterday: it is read when a picker mounts.
  - **Typography (2.9, `/emil-typography`, `/emil-design-foundations`).** Nothing new was defined. Measured in the popover: the month heading 14px/600 (the ingested design's `text-fg-secondary`), the weekday labels 14px/500, a day 14px/400, Today, Cancel and Apply 14px/600 (the `Button`'s own), the date field 14px (the `InputDateBase` size `sm`). One scale step, weight and colour carry the levels. Day figures sit in fixed 40px cells, so nothing shifts as a month changes.
  - **Keyboard (1.9 item 5), measured.** Enter on the trigger opens it with focus inside the dialog; Tab runs Previous, Next, the month, day and year segments, Today, the grid, Cancel, Apply; an arrow key moves the day; Escape closes it, keeps the date and returns focus to the trigger. Pick then Apply sets the date; pick then Cancel, Escape or a press outside keeps it. A range: a preset fills the draft, Cancel keeps the old range, preset then Apply sets it ("Nov 1, 2026 to Nov 30, 2026", the name the trigger carries).
  - **Documented (5.3).** `/components/date-picker` in the template order: Playground (single or range, size, "earliest date is today", disabled; a line under the picker says what was last applied or cancelled), Single date, Date range, Calendars on their own, States, API from the real interfaces, Behaviour (the draft, the changes from the ingested source), Usage, and Figma as an honest "not linked yet". Slotted A-Z in `config/design-system.config.ts` (`date-picker`, between `checkbox` and `input`), `lib/nav.ts` (between Checkbox and Dropdown) and the README table. Each edited component file has a note at the top listing what changed from the ingested source.
  - **Checked.** `npx tsc --noEmit`, `npx eslint` on the touched files and `npm run check:contracts` pass; zero console errors on every page walked. Widths 1600, 900 and 600 for the range (two months, the short presets above the grid and the date fields below it from `md` up, one month with the fields above it below `md`).
  - **Not checked.** A touch screen (the 40px targets rely on the `Button`'s hit area, which is the component's own); a screen reader (the names were read from the accessibility tree, not heard); right-to-left and other calendars; `granularity` other than the default; the pickers in a real form, because nothing uses them yet.
  - **Open, for the designer (0.4).** (1) **Does this replace `InputDatePicker`?** The custom date field (`components/custom/date-picker`, the form field of 2.11) also picks a date from a calendar; these are button-triggered, with Apply and presets, so they are not an exact twin, but "the same job" (1.7) is yours to decide, and nothing was migrated. The custom Date range component was removed the same day by another instruction (`2026-11-02-01`), which is why the override reasons now name only the field. (2) **Dates follow the browser's language** ("Nov 15, 2026" in an English (US) browser): the app has no `I18nProvider`, so every React Aria date does, `InputDatePicker` included. An Australian browser shows "15 Nov 2026". Fixing it to en-AU is app-wide and not made here. (3) Keeping the pick in a draft means `onChange` fires only on Apply; a caller that wants the date to move as it is picked has no prop for that. It was not added.
