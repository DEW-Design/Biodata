# 2026-09-29 - DLA's agreement document is real end to end - "Phase 1: Admin manually uploads the DLA agreement to the tool. Once that's done, user is able to download it on their end," per direct instruction

- **Sept 29 2026: DLA's agreement document is real end to end - "Phase 1: Admin manually uploads the DLA agreement to the tool. Once that's done, user is able to download it on their end," per direct instruction.** `agreementFile: { name: string } | null` had existed since DLA shipped, but was always a filename only - the Approve Request modal's real `InputFile` control already read a picked file, then threw away everything except `file.name`; "Download PDF" on the deep dive was a `toast.brand("Download isn't wired up yet"...)`, never a real download, for every DLA record including the seed ones that already showed a filename. Scoped to DLA only, per the explicit ask - DSA has the identical gap (`dsa-detail.tsx`'s own "Download PDF" is the same toast) and wasn't touched here.
  - **Real upload:** `agreementFile` is now a real `DlaAgreementFile` (`{name, size, dataUrl}`, `agreement-status.ts`-adjacent home `dla-data.ts`) - `dataUrl` is the picked file's own bytes as a base64 `data:` URL (`FileReader.readAsDataURL`, `readAgreementFile()` in `dla-detail.tsx`, kept out of `dla-data.ts` since it's a DOM API and that module is also imported server-side for `generateStaticParams`). A base64 string round-trips through `JSON.stringify`/localStorage exactly like every other field this store already persists - no new serialisation plumbing needed, unlike a raw `Blob` (which `JSON.stringify` silently reduces to `"{}"`).
  - **The 2MB the `InputFile` hint already advertised ("PDF, PNG, JPG (max. 2mb)") is now enforced, not just advisory** - `MAX_AGREEMENT_FILE_BYTES` (2MB), checked the instant a file is picked; an oversized file shows a real inline error on the field (`isInvalid`/hint, "... is over 2MB - choose a smaller file.") and is rejected before ever being read. A real quota concern, not decoration: a browser's whole-origin localStorage budget is typically 5-10MB, and this store already persists every DLA record plus its full Audit Log in the same blob - one unbounded file could crowd out everything else. The modal also shows a real loading spinner (`InputFile`'s own `isLoading` prop) while the file is being read, and Submit is blocked (`isSubmitLoading`, plus a defensive early return in `onSubmit`) until the read finishes.
  - **Real download:** "Download PDF" (`dla-detail.tsx`) now builds a temporary `<a href={dataUrl} download={name}>`, clicks it, and removes it - a data URL needs no Blob/object-URL conversion first, unlike this app's own CSV/Excel/PDF-export technique (`map-search/export-utils.ts`), which starts from plain text instead. `showAgreement` (Active or Closed) already gated this action to whoever can see the record at all, not just `dlaApproval` reviewers - so the requester genuinely already reaches this button today, it just needed to do something real.
  - **The 3 seed records that already carried a filename** (`DLA-2025-01348`, `DLA-2024-00219`, `DLA-2026-00510`) got a real, valid one-page PDF instead of a bare string - `placeholderAgreementFile(id)` in `dla-data.ts` hand-builds a minimal but genuinely correct PDF (real objects, a computed xref table, the built-in Helvetica font, no external assets), with its own text honestly labelled "This is a placeholder document. This preview does not store a real signed agreement for it." - not fabricated agreement content, an honest marker (CONTRACTS §0.3), the same instinct as `mockToken()`'s own "never a real credential" comment elsewhere in this file. Every approval made through the real modal from here on attaches the requester's own real uploaded bytes instead.
  - Verified `tsc --noEmit`/`eslint --max-warnings=0` clean, `npm run check:contracts` clean, and the real Pages build (`PAGES_BASE_PATH=/Biodata next build`, all `/pages/dla/[id]` seed routes including the 3 with a synthesised PDF prerendered with no error - confirming `btoa` at module-eval time is safe in that build's Node runtime too). Live (Playwright, a disposable install discarded after, `package.json` untouched): picking a 3MB file on Approve showed the real inline "over 2MB" error and blocked it; a real small PDF was accepted, approved (moved the request to Active by backdating the grant start date in the real segmented `InputDate` fields), and the resulting "Download PDF" click produced a file byte-for-byte identical to the one uploaded; reloading the page in the same browser session (a real localStorage round-trip, not a fresh profile) kept the file intact and "Download PDF" still produced the identical bytes; a registered user (the requester, not the approving admin) saw and could use the same real button; a seed record's placeholder PDF downloaded as a real file starting with `%PDF` containing its own honest placeholder text.
