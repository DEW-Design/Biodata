# 2026-09-29 - the decision index is generated and CONTRACTS.md loads by scope

- **Sept 29 2026: the decision index is generated from the files, a decision is created with a command, and CONTRACTS.md is loaded by scope instead of whole, per direct instruction ("Can we make this happen?").** Two scaling problems from the review: a shared log edited by hand (two sessions had already collided on it) and a contracts file loaded whole in every session.
  - **Generated index.** `scripts/build-context-index.mjs` writes `context/decisions/INDEX.md` from the decision files (`npm run context:index`). It moved out of `CONTEXT.md` on purpose: it is a lookup table of about 8k tokens, so it is no longer loaded into every session; sessions read or grep it when a task needs history. `CONTEXT.md` fell from about 38k to about 27.5k tokens and now holds only standing reference plus a pointer. Titles are shortened to 110 characters.
  - **`npm run decision:new -- --title "..."`** (`scripts/new-decision.mjs`) creates the next numbered file with the exclusive-create flag, so two sessions choosing the same number cannot overwrite each other (tested with three simultaneous runs: three files, none lost), then rebuilds the index.
  - **`AUTO §5.1b`** fails when INDEX.md is out of date with the files, or when a dated entry is appended to `CONTEXT.md` (the exact failure that happened after the split). §0.6 item 6 and §5.1 rewritten; §0.1, §9.1 now say "indexed in `context/decisions/INDEX.md`".
  - **Scoped contracts (new §5.5).** `CONTRACTS.md` stays the one canonical text with unchanged clause numbers. `scripts/build-contract-rules.mjs` (`npm run contracts:rules`) generates `.claude/rules/contracts-*.md` from it using `contracts/rule-scopes.json`. The core (how to read, Part I, process rules, and a one-line index of all 52 clauses and which file holds each) has no `paths` and loads at launch; build, components, shell, docs and governance carry `paths` and load when a matching file is read. The `@CONTRACTS.md` import was removed from `CLAUDE.md` and from the top of `CONTEXT.md`.
  - **`AUTO §5.5`** fails when a generated rule file is hand-edited or stale, or when a clause has no scope (so a new clause cannot be added without deciding where it loads).
  - **Measured (chars/4, approximate):** full CONTRACTS.md ~9.6k tokens. At launch now ~3.8k (-61%). A session touching `components/**` loads core + build + components ~7.0k (-26%); `scripts/**` or `contracts/**` ~4.3k (-55%); a doc page ~6.7k (-30%). A session on `app/pages/**` loads core + build + shell ~9.4k, so **no saving there**: that work needs almost every clause. The real saving is elsewhere, see below.
  - **Verified:** every failure mode was provoked and caught (hand-edited generated file, new clause with no scope, dated entry appended to CONTEXT.md, new decision file without an index rebuild) and each was restored; `npm run check:contracts` clean; `eslint --max-warnings=0` clean on the four scripts; the Claude Code docs were read first: path-scoped rules trigger on READING a matching file (not on creating one), rules without `paths` load at launch. That is why the core carries the clause index and §5.5 requires reading the scoped file first when starting a new file. Confirmed in practice: the governance rule file was injected into this very session when `scripts/` and `contracts/` files were touched.
  - **Not verified:** the launch-time load in a brand-new session (check `/memory` there, or the `InstructionsLoaded` hook, which lists what loaded and why). Token figures are estimates, not measured by the tool.
  - **Open, recommended next:** `CONTEXT.md`'s standing reference is still about 27k tokens loaded every session, three times the size of CONTRACTS.md. The same mechanism would scope it by topic (doc-page template and QA check only for `app/*docs*` and `components/**`, BDBSA research only for map-search and data files, role model only for role code). Not started: it moves content the designer has not been asked about. Not committed.
