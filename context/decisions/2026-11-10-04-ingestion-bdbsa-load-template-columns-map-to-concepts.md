# 2026-11-10 - Ingestion: BDBSA load template columns map to concepts; new event types and hierarchy

- **Nov 10 2026: the data ingestion stress test reads BDBSA's own column names as our concepts, and takes the business's event comments (Tranche 2 left out).** The designer loaded `TestDummy_ElectLoad_fuzzed5.xlsx` (the BDBSA Electronic Load Tool template: SITE 25 rows, VISIT 25, SPECIES 806, and a NOTES tab) into the sandbox: "a few concepts are not getting mapped correctly", and the business's comments (screenshot) "excluding the Tranche 2 items need to be addressed, and then we run the same dummy data load to stress test again". Tranche 2 (linking two projects, custom event structure and templates, print dataset and upload, the mobile app) is not touched.
  **The fault.** A column was matched to a field only by its own text, so CAMPNAME never reached Site Name, LOCMETHODNR never reached Location Method, and so on (the Known Gap "Real column names rarely match our schema's field names"). 112 species rows were also reported as errors for carrying VOUCHERTYPE, and every SITE row for SITESLOPE and SITEASPECT.
  **Mapping (`config/data-model-schema.ts`).** `BDBSA_COLUMN_ALIASES` / `bdbsaAliasesFor`: derived from `BDBSA_KEY_CROSSWALK` (a value that is one column, or a Fauna column and its Flora spelling; composites and notes give nothing), plus `BDBSA_EXTRA_ALIASES`, each with its reason. The page reads a field from its own name, `FIELD_ALIASES`, or these. The field is still stored under our name (the earlier decision). Extras beyond the crosswalk: VISITDATE as Visit Start Date (the Known Gap on Start Date already says the Heathfield export and, now, this template carry it); OBSDATE as an Observation's Start Date (the duplicate-header Known Gap names it "Observation Date"); OLDEASTING and OLDNORTHING as Community and Non-biotic Easting and Northing (the crosswalk's text is composite); and the Voucher section of an Individual Occurrence by name (VOUCHERTYPE, VOUCHERSERIESNR, VOUCHERNR, DETERMINEDATE, DETERMINERNR1, DETERMINERNR2, VOUCHERTRANSDATE). The voucher group is a claim by name only: no export or code table confirms it.
  **Carried concepts.** `carriedFieldsFor`: a real row carries concepts its own record type's template lacks (SITE: the landform, geology and soil columns; VISIT: fire scars, bare earth, litter, climate, vegetation condition and structural formation; a species row: the other Observation types' columns; a Population Occurrence: the voucher columns). They are kept on that row under the concept's own name, flagged "double check this", with a note naming the column and the record type whose concept it is, and are no longer errors. No record is made for them: whether a SITE row's landform columns become a Non-biotic Observation is still the open Known Gap (updated). The voucher columns now move to the Occurrence with the other identity columns.
  **Business comments.** (a) Two event types, Opportune and Point intercept, in `VALID_TYPES_BY_KIND` and `FIELD_SCHEMA` (`eventFields`, the sections the other sampling events share: no record-page frame exists for either); they appear on `/config/data-model` automatically. (b) Any event can have any event; the one exception, a Block cannot have a Ramble (`EVENT_NESTING_EXCLUSIONS`, `isEventNestingBlocked`; the error reads `A Ramble can't sit inside a Block ("BK1")`); an Observation sits under an event or a sub-event. This replaces the rule that a Site cannot sit under a Visit, so a Site under a Visit is no longer an error: the business note reads "Any event can have any event" and names one exception. (c) A blank name gets the type and a sequence number, after linking, so a made-up name is never read as a pointer: an event is "Opportune 1", an occurrence or observation says which it is ("Population occurrence 3", "Community observation 12"). The number is the record's place among its own kind and type in the upload, so no two share one; a name the file gave is kept; the JSON comment says "auto-named". (d) Site gets Start Date, End Date, Duration and Date Accuracy, after its existing fields, as optional concepts (`OPTIONAL_FIELDS`, shown on the docs page as "Optional, under Manage concepts"). Nothing in the schema is required, so "optional" is a label here; the Manage concepts control itself is on the project page, outside this pass.
  **Sample data.** The deliberately broken Site-under-Visit row is now a Ramble in a Block; a Block, an Opportune and a Point intercept inside a Transect were added as good records.
  **Result on the dummy file (the same file, before and after).** Records 1,662 both times. Valid 1,453 then 1,586; with errors 209 then 76. The 76 are 38 species Occurrences and their 38 Observations, unplaced because their coordinates match no Visit: 12 rows say 515303, 7105930 on 43377 where the Visit is 515203, 7105930; 26 rows say 516901, 7115383 on 43371 where the Visit is 516901, 7115283. That is fuzzed data (a digit changed), and refusing to place them is the right result. The other 133 records with errors were the tool's: VOUCHERTYPE on 113 Observations and SITESLOPE or SITEASPECT on 22 Sites (a record could carry both a mapping error and, for the 76, the placement one). Fields with a value that read as a template field: Site 1 then 7 (Site Name, Altitude, Location Method, Datum, Reliability, Location Comment, Photopoint Marker Present); Visit 0 then 4 (Visit Name made by the naming rule, Visit Comment, Start Date, Photopoint Direction); Community Observation 1 then 6 (Date Accuracy, Start Date, Zone, Easting, Northing, Observation Name made by the rule); Individual Observation Comment 0 then 12; the Individual Occurrence's voucher section 0 then 5 fields on the one row that has a voucher. Sample data: 21 records, 13 valid, 8 with errors (the same as before). Sample workbook: 19, 17, 2.
  **Still unmapped, and why.** Sort_ID, SITETYPE, RECSTATUSCODE, RECSTUTUSCODE: no concept in the crosswalk or the Known Gaps (RECSTUTUSCODE is also a misspelt header in this file, and Occurrence Status is unconfirmed, so it is not guessed). CAMPMAP, QUADSITE, PATCHQUAD: the parts of the Site key (Legacy Site ID is a composite with no single column). OLDZONE, OLDEASTING, OLDNORTHING on Site and Visit: a Site has no coordinate fields (Known Gap), the sandbox reads them to place the records. STREWCOMM, VEGDATE, PHYSDATE, PHOTODATE, PHOTOFILENAME: no concept of that name. VEGQUADSIZE1 and VEGQUADSIZE2: a per-visit composite with no Visit field. PLANTOBS1, PLANTOBS2, PHYSOBS1, PHYSOBS2: the per-group observer slots (Known Gap, undecided). MUSEUMHERBMNR, PREFIX, ACCURACYCODE, VOUCHERCOMM: voucher columns with no field of that name. Columns with no data in this file (TIME, LINENR, METHODNR, the tree health columns and the rest) are mapped by the crosswalk but could not be exercised.
  **Assumptions to confirm (0.4).** (1) Dropping the Site-under-Visit rule. (2) The wording of an auto-name ("Population occurrence 3"), and that the number is the place among its type, not the count of unnamed ones. (3) OBSDATE as Start Date, and the voucher names. (4) Carrying the Non-biotic and Community columns on the Site and Visit row, flagged, rather than making a Non-biotic Observation under them. (5) Opportune and Point intercept take the shared sampling event sections; an Opportune record is probably a point with coordinates. (6) A tab or file cannot be classified as Opportune or Point intercept by its name, and a reference column ("Block ID", "Opportune ID") is not read as a parent: only Kind, Type and Parent ID place a sub-event, as before. (7) `custom-concepts.ts` (the dataset upload form's list of known concepts) reads the crosswalk's columns but not these extras (VISITDATE, OBSDATE, the vouchers), so those may still show as custom concepts there; it is outside this pass.
  **Not verified.** The Manage concepts behaviour for Site temporal fields (project page, another pass); the project record rules and Add Project (other forks). Verified in a browser at 1440x1000 with the dev server, zero console errors: the dummy workbook (counts above, JSON of a Site, a Visit and species rows read), the sample data and sample workbook, and a 12-row CSV with the two new types, sub-events, a Ramble in a Block (error), a Site under a Visit (accepted) and Observations under a sub-event. `tsc`, `eslint` on the touched files and `check:contracts` pass. Not committed.
- **Nov 10 2026, continuation: Opportune and Point intercept take the business's own frames.** The designer attached the field frames for the two event types (read from a transcription, not the images). They replace the shared sampling event sections used earlier the same day (`eventFields`), which had been a stand-in because no frame had arrived.
  **Fields (`frameEventFields`).** Name ("Opportune Name", "Point intercept Name"), Description, Source ID, Record Status, Observers (one field: the frame says Observers and marks it a new column, so not Observer 1 to 3), then Geometry as the coordinate fields (Zone, Easting, Northing, Latitude, Longitude; Opportune also Location Details, where a polygon or shapefile goes, as in the Ramble and Block frames; Point intercept is coordinates only), "Location Method & Desc" (the repo's "X & Desc" convention for a code and its name; the plain "Location Method" still reads as it, `FIELD_ALIASES`), Datum, Reliability, Sample Site Dimensions (Opportune only), Location Comment, Start Date, End Date, Date Accuracy, Duration, Observation Time, Comment Type, and the comment ("Opportune Comment"). No IBRA and no Photopoint fields. The ID is the record's ID column, not a field, as for the other events. The last words of the Point intercept Geometry note ("Must be a child event, Optiona...") are cut off in the copy we hold and are not read.
  **Required.** The schema had no notion of a required field. `REQUIRED_FIELDS` is the one place that says so, with a three-line check in `validateRecords`: Location Comment must have a value on both types (`"Location Comment" is required on an Opportune`). Nothing else in the schema is required.
  **Point intercept must be a child.** A Point intercept with no parent is an error and unresolved ("A Point intercept must sit inside another event"); under any event, a Site and a Visit included, it is fine.
  **Inherit from parent.** When Start Date is blank on either type, `applyInheritedStartDates` takes the parent event's (following the chain, so a Point intercept in an Opportune in a Site takes the Site's) and the JSON comment says "inherited from the parent event <label>, because no start date was given". A parent with no start date, or the Project as parent, gives nothing: no date is made up.
  **A guard, because the new names are common.** "Observers", "Record Status", "Observation Time" and "Comment Type" now exist in the schema, so a column with one of those names on a Site or an Occurrence row would have been reported as "a different record type's field". `CROSS_TYPE_FIELD_NAMES` leaves the names only these two types use out of that check, so such a column is flagged for review as it was before.
  **BDBSA mapping.** Empty for both types: they are new and no legacy column is known. The known gap about them is rewritten (history kept: first built on the shared sections, then the frames).
  **Verified.** The dummy file again: 1,662 records, 1,586 valid, 76 with errors (the same 76 unplaced by two changed coordinates); sample data 21, 13, 8; sample workbook 19, 17, 2; the same field counts per type as before. A 14-row CSV: an Opportune under a Site with no start date inherits the Site's (2026-10-01), a Point intercept under that Opportune inherits through it, a Point intercept under a Visit takes the Visit's, a Point intercept under a Block with its own date keeps it, a Point intercept with no parent errors, an Opportune with no Location Comment errors, a Ramble in a Block errors, a Site under a Visit and Observations under a sub-event are accepted, and an "Observers" column on a Site row is flagged, not an error. `tsc`, `eslint` on the touched files and `check:contracts` pass; zero console errors. **Not verified:** the frames themselves (transcribed, not seen); the Point intercept note; a polygon in Location Details (no file carries one); and whether a sub-event's inherited date should follow a later edit of its parent (it is read at ingestion only). Not committed.
  **Question for the designer (0.4).** The Opportune frame's Geometry and Location Details both take a place: here the coordinate fields are the Geometry and Location Details the polygon. Is that how the frame means "coordinates, polygon etc", or is Geometry a single field holding whichever of the two it is?
- **Nov 10 2026, continuation 2: the structure columns stop appearing as leftover rows, and the placement keys gain the Zone.** The designer opened Site YUP-005-01 from the dummy load and saw Sort_ID, SITETYPE, RECSTATUSCODE, CAMPMAP, QUADSITE, PATCHQUAD, OLDZONE, OLDEASTING and OLDNORTHING as raw rows: "these need to map back correctly to the UI concept names ... OLD zone, Easting, Northing -> link to zone, easting, northing. Sort_ID, SITETYPE, RECSTATUSCODE, CAMPMAP, QUADSITE: we're not using these either, they're already mapped."
  **Zone, Easting, Northing.** Every type whose schema has them (Ramble, Opportune, Point intercept, Community, Non-biotic) now reads OLDZONE, OLDEASTING and OLDNORTHING as those concepts (`bdbsaAliasesFor`, from the schema itself). Site and Visit have no such concepts in their frames (the Known Gap on Site's coordinates, still open), so there they are structure only: used for the placement, not shown on the record, and named in the tab report. A coordinate is shown as the number the file holds: a cell formatted 0.000 read "537003.000", now 537003 (only an all-zero fraction is dropped), on the fields and on the placement keys alike.
  **Structure columns (`STRUCTURAL_COLUMNS`).** Sort_ID, SITETYPE, RECSTATUSCODE (Site and Visit), CAMPMAP, QUADSITE, PATCHQUAD, SURVEYNR, VISITDATE and the coordinates are consumed by the structure and are no longer fields. The Summary tab's "How the tabs were read" has a new column, "Columns used for the structure, and not used": per tab, "Used for the structure" and "Not used" lines naming each column present and why (one line per rule). A Site's "Legacy Site ID" is filled with the three key columns joined (ASA-002-01), which the crosswalk names as its composite; the JSON comment says so. A species row's RECSTUTUSCODE (the template's own misspelling) or RECSTATUSCODE moves to the Occurrence as "Occurrence Status": an assumption matched by meaning, as no code table says what U and Q stand for.
  **Linking (the designer's traceback, ref-domain.md).** The keys now include the Zone: a Visit finds its Site by Survey Number, Zone, Easting and Northing; a species row finds its Visit by the same and the visit date; the Observation sits under its own Occurrence; a Site's ID is CAMPMAP-QUADSITE-PATCHQUAD (a one-digit patch/quad padded); the Project is the Survey Number. Numbers are compared as numbers; the Zone is compared only when both sides have one, otherwise the key falls back to Survey Number, Easting and Northing as before; on a shared key the later record is used, as before. The code read against it: `resolveNaturalKeyRelationships` (the keys, changed), `normalizeSiteId` and `padSiteSequence` (correct), `expandSpeciesOccurrences` (the Observation's own Parent ID; correct).
  **Verified by recomputing the tree from the raw sheets** (`/tmp/xl/link.cjs`, an independent script, not the page's code): 25 Sites, every Visit under the Site with the same Survey Number, Zone, Easting and Northing (25 of 25, no orphan Visit); the Site ids built are the recomputed ones (ASA-002-01 style); per Site the number of Visits and of species Occurrences is identical to the recomputation (0 differences); per Visit the species count is identical (23 Visits have species, 0 differences); 768 species rows placed and 768 Observations each under its own Occurrence; the same 76 records unplaced, for the same reason (12 rows say 515303, 7105930 on 43377 where the Visit is 515203; 26 say 516901, 7115383 on 43371 where the Visit is 516901, 7115283). No Site, Visit or species was linked to a different Site than the recomputation says. The Zone changes nothing on this file: all three tabs have 25 keys with or without it (zones 53 and 54), so the keys were already unique; it matters for a file where two places share an Easting and Northing in different zones. Result: 1,662 records, 1,586 valid, 76 with errors (unchanged); sample data 21, 13, 8; sample workbook 19, 17, 2; zero console errors.
