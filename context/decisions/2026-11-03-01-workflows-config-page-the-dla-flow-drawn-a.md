# 2026-11-03 - Workflows config page: the DLA flow drawn, a sandbox to run it, and the gaps it shows

- **Nov 3 2026: a new config page, `/config/workflows`, for seeing how business rules work.** The designer: (1) "since we're using the name notifications in notification management, we'll call 'notifications' from UX to 'Activity'. E.g., if a data has been uploaded, and it comes to an admin for review, it has to come up as an activity notification on the admin panel"; (2) "a new config page ... a way to visualise how Business rules are working. And a sandbox for us to see how the workflows hold up, and identify any gaps we can fix. We'll work through one flow at a time, starting with DLA." After a proposal and four questions the designer answered only the address ("like /config/workflows"), so the defaults below were taken.
  - **Activity, as read.** What a person sees in the product when something needs them or has happened to their request. Notification Management stays the admin tool for what is sent and when (email only today). No Activity surface exists yet: nothing in the product tells an admin a request is waiting, and Home's task list is seeded text. Where Activity shows (a header bell, a panel on Home, both) is not decided; the page previews each person's feed so that design can start from the real events. Every Activity line on the page is marked Proposed.
  - **Built.** `config/workflows/dla-workflow.ts` writes the DLA flow as data (13 moves: who makes each, from and to which status, what it needs, where the product builds it, and the proposed Activity), with 9 gaps, in the way `/config/data-model` reads `config/data-model-schema.ts`. The page (`app/(docs)/config/workflows/`, reached by its address like `/config/data-model`, not in the docs navigation) has three tabs. **Rules:** the flow as a picture (the real status badges, a press on a status filters the table to its moves), a table of every move (who, what it needs, Activity, and the email Notification Management would send, read live from this browser's notifications), a role-by-move grid from `hasFeatureAccess` for all seven roles, and two checks against the product (every status appears; editing is offered in the statuses `isDlaEditable` allows). **Sandbox:** one request, walked through its life as any of the seven roles with a clock (1, 14, 60 days, or to the day after the end date). It uses the product's own `autoTransitions` for the clock's moves, `hasFeatureAccess` for access and the notifications for email, replicates the stores' moves (including Approve landing on Active if the start date has arrived, and Cancel logged as the requester), shows what the role can do now and, for the rest, why not, the Activity each person would see, the emails sent and the Audit Log. It touches no store. **Gaps:** nine findings, each with why it matters and a proposed fix, in the form of the data model page's gap cards; one closes itself when Notification Management gains an email for Active.
  - **What the sandbox showed (run, not only read).** (a) A registered user cannot answer a hold: while On hold they can edit and cancel, and only a reviewer can resume. (b) Approving with a start date of today lands on Active and sends no email, because the one DLA email (NTF-011) fires for Approved and Rejected only; with a start date 14 days out it emails at Approved and then says nothing when the clock makes it Active. (c) The admin is told nothing when a request is submitted, the requester nothing when it is picked up or held. The rest of the nine, read from the code: Put on hold takes no reason; edits during review are not told and not logged; an admin's cancellation is logged as the requester's; every review move is logged under one fixed reviewer name; Add location on an Active agreement has no review; the 60-day expiry warning is a banner only.
  - **Source and limits (0.3, 0.5).** The rules are the product's as the code has them today (`dla-detail.tsx` for the buttons each status shows, `dla-store.ts`, `agreement-status.ts`, `role-access.config.ts`). They are **not** checked against the business's "DLA/DSA Users Workflow Status" sheet, which was asked for and not provided; the page says so. The product does not read the definition yet, so it can drift: only the two checks above guard it. The 60-day reminder window is copied by hand into the sandbox.
  - **Slice 2, not started (0.4).** Move `dla-detail.tsx` and `dla-store.ts` onto the definition so the page and the product cannot disagree. It changes product code, so it waits for the designer.
  - **Checked (0.6).** `npx tsc --noEmit`, `npx eslint` on the new files and `npm run check:contracts` pass. Live, zero console errors, at 1440, 900 and 600px with no page overflow: all three tabs; the diagram's status buttons by mouse and by Enter; the moves table fits its column (926px, no scroll); the sandbox run end to end (submit, start review, hold, resume, approve today and in 14 days, the clock to Active and to Closed, a public user who has nothing to do). Typography (2.9): no new type layer; the page is doc chrome (Geist) around the DEW Badge, Table and Tabs, and the sandbox controls are Scaffold's.
  - **Not checked.** A screen reader; the page against the business sheet; the Super Admin's grid column beside the Admin's (identical by the access rules); another flow (DSA, nominations, dataset review), which is the next one.
  - **Open, for the designer (0.4).** (1) The workflow sheet, so rules can be checked and not only read. (2) Slice 2: the product reads the definition. (3) Where the gaps live: in the repo (as built, `DLA_GAPS`) or in the browser. (4) Whether the page should be linked from `/config` or the docs navigation (it is not, like the data model page). (5) Where Activity shows, and whether Notification Management configures it as a channel next to email. (6) The proposed Activity lines: keep, change or drop each. (7) Which flow is next. (8) Not committed or pushed.
  - **Continued (same day): the business rules are mapped onto the workflow.** The designer: "DLA -- workflow's already in the prototype with the business rules I gave. Next step, we can map the actual BR to the workflow." The rules were gathered from what is recorded, not from the sheet itself (which is not in the repo): the workflow sheet and the Slack answers as quoted in `2026-09-24-04`, and the designer's own instructions in `2026-09-23-03`, `2026-09-25-18` and `2026-09-29-37`, `-38` and `-43`. A new tab, **Business rules** (`business-rules-view.tsx`), lists them as `DLA_RULES` in `config/workflows/dla-workflow.ts`: 15 rules (BR-1 to BR-15, numbers this page's own), each with the wording as recorded, who gave it, the decision that holds it, what it governs (statuses and moves), a verdict, how the prototype treats it, and the related gaps. "Show on the flow" lights the statuses and lines a rule governs (the diagram takes `lit`, and `MOVE_EDGES` says which line each move is). The Rules tab's moves table carries the BR badges of each move. A filter shows only the rules not fully met.
  - **What the mapping shows.** 11 met, 3 partly met, 1 open question. **Partly:** BR-1 (Cancelled "reachable from anywhere before Closed": a Draft is deleted, not cancelled); BR-3 (a reviewer's manual Start review is built, but "notifications to reviewers for action" is not: this is the rule that asks for Activity); BR-7 (Closed "may be closed automatically upon expiry": the clock does it, nobody can close by hand, and the decision's "or manually" is the build's wording, not the sheet's, and sits against BR-4's "only cancel" for Active). **Open for the business:** BR-8, the sheet's "Auto Approve" path beside Approved, which no recorded answer defines, so the prototype has none. **In the prototype with no rule behind it:** the 60-day expiry banner (the build's choice). The rule texts were not paraphrased into quotes: where the recorded wording is the build's own summary of the sheet (BR-1, BR-7, BR-9's reason, BR-13, BR-14, BR-15) the card says so.
  - **Checks that run (`rule-checks.ts`).** Twelve of the 15 rules have a run, 25 lines in all, each saying what it ran against. "The product's own code" (`isDlaEditable`, `hasFeatureAccess`, `autoTransitions`) proves a fact about the product; "this page's rules" runs the definition through the sandbox, so it proves the page agrees with the rule, and the product only as far as the two were read to match. BR-10 (requested dates locked from Submitted) and BR-12 (the admin uploads the agreement) are in forms and modals, so they were read from the decisions and not run. Every run agrees with its verdict: a rule marked Met has no failing line, and each of the four not fully met has one.
  - **Checked.** `tsc`, `eslint` and `check:contracts` pass; live, zero console errors: the tab, the counts, every rule's lines, lighting BR-1 and BR-4, the filter, the one uncovered move; the four-tab strip now scrolls sideways at 600px (the fourth tab pushed the page 27px wide), page overflow 0 at 1440, 900 and 600px.
  - **Open (0.4).** (1) The sheet itself, for the wording of rules the decisions only summarise (BR-1, BR-7). (2) For the business: what is Auto Approve; is there a manual close and how does it differ from Cancel; may a Draft be cancelled, or is deleting it right; who is told when a request is submitted and how (BR-3). (3) Whether the build's choices with no rule behind them (the 60-day banner, edits during review, Add location without review) should be confirmed or dropped. (4) Slice 2 and the rest of the earlier list stand.
