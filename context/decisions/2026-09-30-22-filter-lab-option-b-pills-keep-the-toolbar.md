# 2026-09-30 - Filter lab option B: pills keep the toolbar one line

- **Sept 30 2026: Filter lab option B: pills keep the toolbar one line.** The designer's screenshots of `/proto/filter-options` option B showed the layout breaking: each filter button carried its values as text ("Validation status: Processing, Successful +1"), so with two filters on the buttons outgrew the row, wrapped under the search box, left the search stranded on its own line and pushed the table down a row. Looked at filter patterns on Mobbin (Deel, Heidi, PandaDoc for count-only pills; Deel, Squarespace, Origin, Wise, Square for overlay drawers; Navattic, Remote, Asana for a separate strip of what is on; Browserbase for the attribute menu with submenus, which is option A; Apollo for the push panel, which is option C's problem). Changed B only: a pill is the attribute's name and, when on, a count badge ("Validation status 3"); the values are in its popover, whose footer now shows the current summary beside Clear; the pill's aria-label carries the summary. The pills sit in their own scrolling region (`overflow-x-auto`, no wrap) with "More filters" and "Clear all" fixed after it, so the toolbar has one line and one height. Measured at 1440, 1100 and 900px wide with 0, 1, 2 and 7 filters on: the search box and the table did not move at any width. Verified: tsc, eslint, check:contracts, zero console errors. Not changed: option C still opens as a sibling of the table and squeezes it (the same class of problem); option A's chips can still add a row when a filter goes on. The reference-based proposal for both (an overlay drawer for C, a separate chip strip that reserves its space for A) waits for the designer's choice (CONTRACTS 2.6: propose and stop). Open: the last visible pill is cut hard at the edge of its scroll area; an edge fade is possible. Not committed.
