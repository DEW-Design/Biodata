# 2026-09-27 - `zustand` brought in for real persistence, per direct request, scoped to "DLA/DSA, Map search for species."

- **Sept 27 2026: `zustand` brought in for real persistence, per direct request, scoped to "DLA/DSA, Map search for species."** DSA and DLA had been the two stores this file most often logged as "no backend, a client navigation keeps state, a full reload resets to the seed" - `dsa-store.ts` and `dla-store.ts` are now genuine `zustand` stores with the `persist` middleware (localStorage), keeping the exact same exported function names/signatures (`useDsas`, `saveDsa`, `approveDsa`, ... and the DLA equivalents) so none of their many consumers (the list, the deep dive, the form, `/proto/collection-sidebar`) needed to change. A DSA/DLA record created or transitioned now survives a real browser reload - client-only persistence (this device/browser), still no real server.
  - **New shared file `app/pages/_shared/zustand-persist.ts`** holds the plumbing every persisted store in this build now needs, once, rather than three times: `browserStorage()` (real `localStorage` on the client, a no-op on the server - this build's GitHub Pages static export renders every `"use client"` page once in Node, where `localStorage` isn't a global at all, not just empty, so a bare `createJSONStorage(() => localStorage)` would fail that build) and `useRehydrate()` (every store is created with `skipHydration: true`, so its first client render matches the server-rendered seed data exactly, then this hook fires the real `persist.rehydrate()` once in a `useEffect` after that render has already committed - rehydrating synchronously at store-creation time instead would mean the client's first paint shows localStorage's content while the server-rendered HTML shows the seed, a real React hydration mismatch the moment a persisted record differs from the seed, not just a console warning). `resolve()` (the Approved-to-Active/Active-to-Closed date-based status transition) stays applied at read time in `useDsas`/`useDlas`, from today's real date - not baked into the persisted state - so a record correctly advances even after sitting in localStorage across days between visits.
  - **"Map search for species"**, scoped to Explore's Species view (`species-results.tsx`) own filter selections - Family/Genus/Species/Information Authority/Licence - in a new `app/pages/_shared/map-search/species-filter-store.ts`, so re-opening Explore keeps the taxonomy you were narrowing to. `Set<string>` values aren't JSON-serialisable by default (`JSON.stringify(new Set(["a"]))` is `"{}"`) - `zustand-persist.ts` gained `setAwareJsonStorage()`, a `createJSONStorage` replacer/reviver pair that tags a Set as `{ __set: [...] }` going out and rebuilds the real `Set` coming back in, so the rest of the component keeps using `Set`/`.has()`/`toggleInSet` exactly as before with no other change.
  - **Deliberately not persisted, and said so rather than silently decided:** the date-range filter (`dateFilterOn`/`dateRange` stay local - a `DateRange`'s `start`/`end` are real `CalendarDate` instances with methods, not plain data, and round-tripping those through JSON is a separate problem this pass didn't need to solve to be useful) and, the bigger one, **the search areas themselves** (drawn shapes, park picks, uploaded shapefiles - `manualBoundaries`/`selectedParkIds`/`shapefileLayers` in `observations-search.tsx`). That state is tightly wound around this exact file's own `?q=`-from-the-header-search render-time reset logic and Leaflet's map lifecycle, both the subject of 25+ hard-won rounds of fixes already logged above - reworking it to rehydrate from localStorage on top of that existing logic is real, separate work, not a drop-in, and this file's own history is full of exactly this class of subtle timing bug. Logged as an honest limitation: a restored species filter has nothing to apply to until the user re-runs a search, until that follow-up is asked for.
  - Verified `tsc --noEmit`, `eslint --max-warnings=0` and `npm run check:contracts` clean; the real GitHub Pages static export (`PAGES_BASE_PATH=/Biodata npm run build`) succeeds with no `localStorage is not defined` error, confirming the SSR guard; a live Playwright pass (installed for the session, removed after - `package.json`/`package-lock.json` show only the real `zustand` addition) end to end: created a real DSA draft, reloaded, the organisation name was still there and `localStorage['biodata-dsa']` held 15 records (14 seed + 1); put an existing DLA request On Hold, reloaded, it was still On Hold, `localStorage['biodata-dla']` held 9 records; checked "Level 1 - Public Access" in Explore's Species "All Filters" panel, confirmed `localStorage['biodata-explore-species-filters']` held `{"__set":["Level 1"]}` (the Set-aware serialisation working), reloaded, the checkbox was still checked - zero console errors across all three.
