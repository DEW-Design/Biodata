# 2026-10-01 - Notification Management round 2 list recipients audit log and the toolbar gap contract

- **Oct 1 2026: Notification Management round 2: list, recipients, audit log, and the toolbar gap contract.** Follows 2026-10-01-02, on the designer's review.
  - **List back to a table.** The designer turned down the split view with the preview beside the list. The list is Controlled Vocabulary's pattern again (CONTRACTS 4.2): Notification (name over description), Sent, To, Category (under "All" only), Status, Updated; a row opens the notification's page, whose Preview tab shows the email. The 4.2 override logged in 2026-10-01-02 is withdrawn. Filter adds Event and Updated.
  - **New clause, CONTRACTS §4.2d "One gap under the header", `AUTO §4.2d`.** The designer: "The spacing for search and filter looks wrong. This error is recurring fix it and add to contracts", and asked to review the clause. The list body under `</SectionHeader.Root>` sits in one `p-6` wrapper; `px-6 pb-6` left the search flush against the header's divider. The check (scripts/check-contracts.mjs) fails a file with `<ToolbarSearch>` where no `div` between `</SectionHeader.Root>` and the first `<ToolbarSearch>` carries `p-6`, `pt-6` or `py-6`. Run before fixing, it failed exactly the two offenders (this list and the project's Datasets view) and none of the ten correct lists; both are fixed. Earlier occurrences are not named in the decision log or git history by that wording; the designer reports it as recurring (0.8). `npm run contracts:rules` regenerated the scoped rules. **Waiting for the designer's review of the clause wording.**
  - **Categories can be created.** Category is a ComboBox: choose one, or type a new one, which is added when the notification is saved ("It is added when you save"). Categories are kept in the store (the Figma's eight, then each added one). Column 2 gets Controlled Vocabulary's finder past six categories and scrolls on its own, Actions in reach.
  - **Recipients simplified** (the designer: "this page is very complex, simplify it", "picking roles and users is very counter-intuitive"). One To field, read like an email's: the chosen recipients as tags (remove with X), a search below that adds one at a time. Roles and people come from User Management (`useRoles`, `useUsers`), so the picker offers whoever an admin has set up; a custom role shows its organisation, since several share a name. "The person it's about" comes from the event and is the default. CC and BCC appear on "Add CC" / "Add BCC". Sender name, reply-to and the email log sit in a collapsed "Sending options" card whose title summarises them. The suggestion list opens as you type or with Down (`menuTrigger="input"`): opening on focus reopened it after every pick, over Add CC and the controls below.
  - **Email log, period or date.** One select, "Keep a copy of each sent email": 6 months, 1 year, 2 years, 7 years, Until a date, Indefinitely, Don't keep a log. "Until a date" reveals a calendar date field (from tomorrow), required, checked to be after today.
  - **Attachments.** "Attach files" in the Message section; each file listed with its size and a remove button, shown at the foot of the email in the preview, in Settings and in History. Only names and sizes are kept in this preview build (no backend).
  - **Rich text editor, not yet.** The designer approved bringing in the Untitled UI editor the safe way (CLI in a scratch copy, as the modals were). The CLI was run in the scratchpad copy only: `text-editor` exists but is a PRO component ("To access PRO components: npx untitledui@latest login"). The login is the designer's to do; credentials are not entered for them. Until then a `<Gap>` marks the toolbar above the message (1.2) and the message keeps its two plain-text marks. No dependency was added and `components/` is untouched.
