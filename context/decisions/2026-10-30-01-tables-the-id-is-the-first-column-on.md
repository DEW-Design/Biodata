# 2026-10-30 - Tables: the ID is the first column on every list that has IDs

- **Oct 30 2026: a table that lists records with IDs of their own leads with the ID. Users, Roles and Permissions gain an ID column, the Vocabulary list moves its ID from second to first, and the Notifications list gains one.** The designer: "All users, roles and permissions have IDs. Let's have ID as the first column. Keep the tables across the webapp consistent. Except Reports."
  - **Principles at stake (0.10):** 3 One system (the project, request, agreement, nomination, batch and dataset lists already led with their ID; these did not), 5 Make it obvious (a record is found by its ID in the same place on every list). They agree.
  - **What changed.**
    1. **Users, Roles, Permissions** (`um-lists.tsx`): a first column "ID" (USR-1001, ROLE-101, PERM-301), the table's row header, sortable. The name is the second column and stays the link. Widths were rebalanced to 100% again and the minimum table width raised a little for the column (the Users list's organisation column got wider, so it does not wrap more than before).
    2. **Vocabularies** (`cv-list.tsx`): the ID was second, after the name; it is first now, and the name second.
    3. **Notifications** (`nt-list.tsx`): a first column "ID" (NTF-003), sortable; the name second. The notification IDs were only on its record page and its audit log.
    4. **The embedded tables of related records** (`um-detail.tsx`): "Users with this role" gains an ID first; "Roles with access" on a permission had the role's ID as a second line under its name, so it moves to its own first column and the second line goes (an ID is not shown twice, 4.3).
    5. **CONTRACTS 4.2i** says it (the ID first, as the row header, in the project list's quiet treatment; not repeated under the name; applies to lists and to embedded tables of related records; the exceptions below), and the scoped rule files were regenerated.
  - **Left as it is, because it already led with an ID:** the Projects list ("Project ID"), the DLA and DSA lists ("Request", "Agreement"), Nominations ("Nomination"), Voucher batches ("Batch"), the project's Datasets ("Dataset") and Records ("ID").
  - **Exceptions.** **Reports** (the designer's own exception: their columns are each report's). Tables whose rows have no ID of their own: the Template Finder (its ids are code slugs), a project's species, its artefacts and its people. **Taxonomy Management's list** was not changed: its identifier is the NSX code, which the higher taxa (orders, families, genera) do not have, so a first column would read "Not provided" down most of its rows.
  - **Checked.** `npx tsc --noEmit` and `npx eslint` clean on the touched files; `npm run check:contracts` passes. Live (Playwright, 1440 x 950, zero console errors): the first column's heading is "ID" and its first cell is a real ID on Users (USR-1012), Roles (ROLE-101), Permissions (PERM-329), a role's Users tab (USR-1001), a permission's Roles (ROLE-101), Vocabularies (BIODATA-106) and Notifications (NTF-003); no ID is cut off by its column and no table scrolls sideways at that width; the Projects, DLA, Nominations and Voucher lists still lead with their ID.
  - **Not checked.** Narrow windows (the new column needs the minimum widths raised above, which is where a narrow window now starts to scroll sideways); touch; sorting by the new ID columns in every list (the sort key is the ID itself).
  - **Open, for the designer (0.4).** (1) The heading of the ID column: the lists use "ID" (Users, Roles, Permissions, Vocabularies, Notifications, Records), "Project ID", "Request", "Agreement", "Nomination", "Batch" and "Dataset". Should each be "ID", the way the new ones are? (2) Taxonomy: should the list lead with the NSX code anyway, with the higher taxa empty, or stay as it is? (3) The Notifications and Vocabulary ID columns are not what the list opens on, so they are not the default sort; the Users, Roles and Permissions lists still open on their name, kind and category.
