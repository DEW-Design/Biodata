# 2026-09-25 - `TextArea` typography now matches `Input`, per page feedback ("the typography in text area looks dubious").

- **Sept 25 2026: `TextArea` typography now matches `Input`, per page feedback ("the typography in text area looks dubious").** Measured live (computed styles, not read from classes): the `Input` renders at 14px Barlow with `px-3 py-2`, while `TextArea` rendered 16px with `px-3.5 py-3` (and `size="sm"` was `p-3`), so a textarea beside an input looked a size larger. Cause: `Input`'s `md` and `lg` sizes ask for the undefined `text-md` and silently fall back to 14px, while `TextArea` used the real `text-base` (16px). Fixed in `components/base/textarea/textarea.tsx`: both sizes are now `px-3 py-2 text-sm` (14px, 8px and 12px padding, same as Input's rendered result); font family was already Barlow in both (it comes from the wrapper). Every `TextArea` consumer (DSA, DLA, Add Project, project-detail editors) picks it up. Sibling grep: `TextArea` was the only field on the real `text-base`; `Input`, `InputNumber`, `InputDate`, `InputTags`, `InputGroup`, `PinInput`, `NativeSelect`, `Select`, `MultiSelect`, `Checkbox` and `RadioButton` all use the dead `text-md` (a known, ratcheted class). **Open, not changed:** whether fields should be 14px or 16px is a designer decision; making `text-md` real would change every field at once. `tsc`, `eslint` and `npm run check:contracts` clean.
