# 2026-10-05 - Pages map lab for the Prototype tools bar, three layouts

- **Oct 5 2026: a "Pages" map for the Prototype tools bar is explored in a lab first, at `/proto/site-map`, before anything is added to the real bar. From the designer: a site map with the structure laid out visually so a person can move between pages quickly, "not on the admin rail but in the prototype tools", and "proto this first so that we're certain what goes into the main /pages/* route".**
  - **Why the Prototype tools, not the rail:** the map is for the person reviewing the prototype (a Scaffold aid, CONTRACTS 1.5), not for a product user, so it must not touch `PrimaryRail` or any persona's navigation (3.4). It is built Scaffold-style in the lab: Geist, react-aria primitives only, the bar's Flinders Violet variables (`TOOL_VARS`, now exported from `status-bar.tsx`), no DEW components.
  - **Three layouts, switched on the bar's Layout tool (`?option=`):** A, Columns: an area per column, a screen's sub-screens indented under it, with a search box; B, Tree: "BioData SA" branching to areas branching to screen chips, with a search box; C, Search first: a "Go to a page" field over the whole list grouped by area (type, arrows, Enter). All three read the same data and show, for the role being viewed, "N of 72 open as <role>".
  - **One list, not two.** The 72 screens that `/pages` already listed by hand moved, unchanged, into `app/pages/_shared/screen-index.ts` (`SCREENS`, `AREAS`); `app/pages/page.tsx` imports them, so the index and the map cannot drift apart. The lab's hierarchy (`site-map-data.ts`) nests a screen under the screen whose path is its longest prefix in the same area. Which pages a role can open reuses the bar's own gate: `isPageBlockedFor` (new export, extracted from `setRole`, same behaviour) plus the role-access matrix for "Signed in", "BioData Admin" and "BioData Super Admin" screens. A screen the role cannot use is dimmed with a lock and the reason, and still opens, so the restriction state can be seen (3.7). Links go through `useRoleHref`, so the role is kept.
  - **Verified live (Playwright, 1708x1024, zero console errors):** all three layouts as BioData Admin (64 of 72 open), Registered User (43) and Public user (22); 72 links (A, B) or 72 options (C) in every role; no horizontal overflow; Geist computed on the headings; a search for "report" in A narrows to 11 links and its first link opens `/pages/reports?userRole=registered-user`; in C typing "nomin" leaves 3 options and ArrowDown then Enter opens `/pages/nominations/new?userRole=biodata-admin`. `npx tsc --noEmit`, eslint on every touched file and `npm run check:contracts` pass. Registered in the `/proto` index.
  - **Not done:** keyboard-only pass of A and B (they are plain links, Tab order only), narrow widths, the other four roles, and a typography pass with the two Emil skills (Scaffold type, sizes taken from the bar's own 14px and 12px). The current page is not highlighted (the lab is not one of the screens). Labs and the `/proto` routes are not in the map (they ship in development only; `labHref`, 5.4).
  - **Open for the designer:** which layout to promote (recommendation: A for scanning the whole prototype, with C's "Go to a page" search as the keyboard path; B is the most diagrammatic but spends the most room). Promoting it needs a panel kind on the bar (the bar's tools are option menus today), and an `AUTO` check that every `app/pages/**/page.tsx` route is in `screen-index.ts` so the map cannot go stale; that check changes `scripts/check-contracts.mjs`, a governance change (9.4), so it waits for approval. The losing layouts are deleted once one is chosen (4.4). Whether the map should also list labs (via `labHref`, development only) is undecided.
