# 2026-10-30 - Submenus: a safe triangle, so a diagonal move does not lose the submenu

- **Oct 30 2026: a menu's submenus have a safe triangle, so the Filter menu (and every other submenu) no longer drops its submenu when the pointer cuts a corner.** The designer, with a post on the tip and a reply to it ("don't close submenus the moment the cursor touches another row ... draw a triangle from the cursor to the submenu's near edge, while the cursor stays inside it keep the submenu open"; "worth adding a short timeout too, so a cursor that stops inside the triangle still swaps rows after a beat"): "could consider safe triangles - for filter submenus across the webapp."
  - **What was wrong, measured.** On the Species tab's Filter, a pointer that opens "Family" and moves diagonally to a low value in its submenu (14 steps, 16ms apart, about what a hand does) crossed the next row and the submenu was gone: the submenu list was empty at the end. React-aria has a guard for this (`useSafelyMouseToSubmenu`), but it samples every 50ms and needs two samples moving towards the submenu before it holds the rows, and a quick diagonal has crossed the first row boundary by then. A slow move survived; a normal one did not.
  - **Principles at stake (0.10):** 5 Make it obvious (a menu does what the hand meant), 3 One system (the Filter menu is on every table; the fix is in the menu, not in each screen, 1.9 and 1.10), 9 Craft shows (a detail a person feels and cannot name). They agree.
  - **What changed (`components/base/dropdown/dropdown.tsx`, `Dropdown.Menu`).**
    1. **The triangle** is drawn from the last point the pointer was on the row that opened the submenu to the near edge of the submenu (a little taller than it is: 8px each way, so aiming at its corner is still safe). It is checked on every event, with no throttle.
    2. **Inside it, moving from one row of the menu to another is not passed on:** the `pointerout` and `pointerover` that would hover the next row are stopped before react sees them (the window, in the capture phase), so the submenu stays. Reaching the submenu ends it.
    3. **Leaving it hands the pointer back at once** (straight down onto the next row swaps in about 160ms, which is react-aria's own hover delay), **and so does stopping inside it for a beat** (220ms, restarted by every move that gets closer to the submenu): the row under the pointer gets the hover it would have had, the row that held it lets go (no row is left looking hovered), and react-aria's own guard, which may be holding the rows, is released.
    4. **A mouse only.** The keyboard (ArrowRight opens, ArrowLeft goes back) and touch are as they were. Because it is in `Dropdown.Menu`, every menu with a submenu has it: the Filter menu on every table, and the record quick actions. The Dropdown doc page says so.
  - **Checked.** `npx tsc --noEmit`, `npx eslint` on the file and `npm run check:contracts` pass. Live (Playwright, 1440 x 900, zero console errors, a pointer moved in steps 16ms apart): a fast diagonal from "Family" to a low value keeps "Family" open (it closed before) and a click on that value ticks it; a slow diagonal keeps it; stopping over the row below inside the triangle holds "Family" and after a beat swaps to "Occurrence type", with only that row focused and hovered; straight down onto the next row swaps in 160ms; moving away from the submenu swaps to the row under the pointer; the keyboard opens and closes the submenu as before; the Projects list's Filter (Status) keeps its submenu on the same fast diagonal.
  - **Not checked.** The record quick actions' own submenu (the same component, not opened); a submenu that opens to the left; a touch screen; a real mouse (the paths are synthetic, 16ms apart, which is a hand's rate and not its jitter).
  - **Open, for the designer (0.4).** The beat is 220ms. The tip suggests "a short timeout"; if it feels slow or quick, it is one constant (`SAFE_TRIANGLE_DWELL_MS`).
