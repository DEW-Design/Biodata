# 2026-10-20 - Business rule: audio and video attachments go to an admin for review

- **Oct 20 2026: Business rule: audio and video attachments go to an admin for review.** The designer: "Just a business rule - if a registered user and above attaches an artefact / attachment, and if its type is audio or video, this will have to be sent to admin for review. We'll need to wire in a workflow for that on production." Answers to the open questions: (1) the reviewers are the BioData Admin and the BioData Super Admin; (2) "Only biodata admin" (read as: a BioData Admin's own audio or video is not reviewed; see Open); (3) show the upload, lower its opacity, with a "Pending review" tag; (4) a rejection takes a reason, "ideally".
  - **The rule:** when a Registered User or any role below the admins attaches an artefact or attachment whose type is audio or video, it shows on the record at once as pending review until an admin approves it. Other types (image, PDF, spreadsheet, link) are unaffected. Audio is kind "video" in the store (`kindForFile` maps mp3, wav and m4a with mp4 and mov).
  - **What shows (prototype, shared with the production Artefacts and attachments tab):** the file shows to everyone, its tile, row or chip at 50% opacity, with a "Pending review" warning tag (`ReviewTag`, `artefact-lightbox.tsx`). On a card the tag sits on the preview area so the tile keeps its height. A rejected file stays, at the same opacity, tagged "Rejected", and the viewer's description says who rejected it and why.
  - **Where it is wired:** `field-notes-store.ts` (`FieldFile.review`, `reviewForNewFile(kind, role)`, `fieldNotesActions.approveFile` and `rejectFile`; `attach` takes the review), the field menu's "Attach a file" (`field-notes.tsx`, which also tells the person in its toast), the lab's Add attachment modal (`add-artefact-modal.tsx`, which says so under the list when an audio or video file is in it and in its toast), the Artefacts and attachments tab (`artefacts-view.tsx`: Approve and Reject icon buttons for a BioData Admin or Super Admin on a pending file, in the cards and in the table; Reject opens the shared `RejectModal` with a required reason), and the two places that shape a file for the viewer (`project-detail-template.tsx`, `project-workspace.tsx`). No new component (CONTRACTS 1.4); `RejectModal` and `ButtonUtility` are reused (0.9).
  - **Production work, not built here:** the real workflow (server-side pending state, who is notified, an admin queue beyond the tab, email, access control so an unapproved file cannot be played or downloaded by others). The prototype has no backend, so the review state is a field on the stored file.
  - **Open:** (1) Q2 read as "an admin's own audio or video is approved as it is attached" for both admin roles (`isBiodataAdmin`, which is true for the Super Admin too); if only the BioData Admin is exempt and the Super Admin's is reviewed, say so; (2) whether the Privileged Admin, who can already resolve questionable values, should be able to review (the answer was admins only, so not built); (3) a pending file still opens in the viewer for everyone in the prototype; production should probably withhold the play and download until approved; (4) a rejected file has no "re-submit" or "remove" step for the attacher beyond the ordinary remove; (5) no notification to the person who attached it, because the prototype's notification list is seeded, not event driven; (6) an admin sees Approve and Reject only on the tab, not on the record's field chip. Not committed.
  - **Verified, in a browser (Playwright with the cached Chromium, a script outside the repo, dev server on :3000):** as a Registered User on the project "Adelaide Hills Bushland Survey", the Add attachment modal with a 2.4 MB mp3 shows the review line, Add shows the toast and the card lands at 50% with the tag; as a BioData Admin the card and table both show the tag, the Approve and Reject buttons only on that row, the table fits its container (no sideways scroll), cards in a row stay level, Reject with an empty reason shows the required error and with a reason marks the file "Rejected" with a toast; zero console errors; `npx tsc --noEmit`, `npx eslint` on all seven touched files and `npm run check:contracts` clean. **Not verified:** Approve clicked in the browser (only the Reject path was run); the field menu's "Attach a file" path (type-checked, not driven); the viewer showing the rejection reason; a Super Admin session; the production project page (shares the same store and tab, not opened); `/emil-typography` and `/emil-design-foundations` on the new copy (the review line, the toasts, the Reject modal text) and the computed styles of the new tag and the 50% opacity (the tag is the design system's `Badge`, `warning` and `error`). Not committed.
